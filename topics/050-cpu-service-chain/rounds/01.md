# Round 1: expose lock-holder preemption

## Question

On each required Linux host, how much longer does a low-priority mutex owner's
5-millisecond thread CPU target occupy in wall time when a
normal-priority CPU hog runs on the owner's logical CPU instead of a third
physical core? How long does a waiter on another physical core remain blocked?

The experiment measures elapsed time, thread CPU time, affinity and nice
readback, per-thread context-switch counts, exact host metadata, and linked
code. It does not identify one Linux scheduler decision, estimate a production
latency distribution, test simultaneous multithreading performance, or compare
the Arm and x86 instruction-set architectures.

## Frozen comparison

- Source: one path-limited Git archive from the Topic 50 source commit.
- Build: the host `cc` compiler with version retained in the receipt and flags
  `-O2 -g -std=c11 -Wall -Wextra -Werror -pthread`.
- Mutex owner: one thread pinned to the selected holder CPU, nice 19, holding
  an ordinary Portable Operating System Interface (POSIX) mutex while
  targeting 5 milliseconds on the per-thread CPU clock
  `CLOCK_THREAD_CPUTIME_ID`. Accepted processes measure from 4.9 through 6.0
  milliseconds.
- Waiter: one normal-priority thread pinned to a second physical core and
  blocked on the mutex.
- CPU hog: one normal-priority thread that runs until the holder releases.
- A treatment: hog pinned to the holder's logical CPU.
- B treatment: the same hog pinned to a third physical core.
- Primary campaign: eight complete four-process blocks, four `ABBA` and four
  `BAAB`, shuffled with fixed seed `500829`.
- A/A control: eight four-process X/Y blocks with mechanically identical B
  settings for both labels, shuffled with fixed seed `500830`.
- Replication: one complete four-process block. Individual processes, process
  identifiers (PIDs), and inner-loop iterations are not independent samples.
- Host total: 16 complete blocks, 64 fresh processes, and, for acceptance, 64
  distinct PIDs.
- Reset: every letter is a fresh process. Failed attempts remain recorded and
  are never replaced.
- Stopping: block counts, seeds, duration, nice value, selected CPUs, and
  commands are fixed before collection.

## Analysis

For holder wall time and waiter blocking time, take the natural logarithm in
each process. Within a block, subtract the mean log value for B from the mean
log value for A. Exponentiating the mean of the eight block contrasts gives
the geometric A/B ratio for each of those two metrics:

```text
d_block = mean(log(A)) - mean(log(B))
A/B ratio = exp(mean(d_block))
```

Report all eight contrasts, their sample standard deviation, and a two-sided
95% Student's t interval. The interval covers between-block variation for this
exact host, binary, placement, workload, and observation window only. It does
not cover other hosts, kernels, processors, builds, times, or applications.

Apply the same calculation to X/Y. This A/A comparison can reveal mechanical
asymmetry in labels, ordering, commands, parsers, or output paths. One fixed
eight-block A/A campaign is not a universal noise floor or a calibrated
false-positive rate.

## Acceptance contract

1. The controller supplies the archive digest, exact 40-character source
   commit, expected hostname, and expected architecture before extraction.
2. The literal Arm target
   `dev-dsk-ahrav-2b-7dc7bd93.us-west-2.amazon.com` reports `aarch64`.
   Runtime-resolved `xxl` reports `x86_64`; both the alias and its current
   backing hostname are recorded.
3. The receipt records kernel, CPU model and features, allowed CPU count,
   selected-core topology and siblings, compiler, build command, scaling and
   idle-state exposure, and readable scheduler controls.
4. The receipt records 256-bit Secure Hash Algorithm (SHA-256) digests for the
   runner, analyzer, independent validator, archive, source files, and native
   binary.
5. Every process verifies exact affinity for all three threads, the holder's
   requested and observed nice value, each thread's start and end CPU,
   positive timings, and the fixed input.
6. All attempts remain in chronological order. A failed or partial period
   fails the campaign and is not silently rerun.
7. On each host, the accepted receipt has exactly 64 rows and 64 distinct PIDs
   across 16 complete blocks.
8. The exact linked holder, waiter, hog, and CPU-burn functions remain
   inspectable in disassembly.
9. The analyzer and structurally independent validator recompute the same
   summaries from raw rows.
10. Measured elapsed and CPU time, observed code generation and metadata, and
    inferred mechanisms remain separate claims.

## Expected signature

This is a preregistered expectation, not a host result. Every accepted process
must record holder thread CPU time from 4.9 through 6.0 milliseconds around the
fixed 5-millisecond target. Treatment A should increase holder wall time and
waiter blocking time relative to B without leaving that range.
Involuntary holder context switches may support a descheduling explanation,
but counts alone cannot identify the exact scheduler path. X/Y should not show
a systematic label effect.

If holder CPU time leaves that range, placement verification fails, nice
readback fails, any process is missing, or the A/A paths are not mechanically
identical, reject the campaign rather than explaining the ratio.
