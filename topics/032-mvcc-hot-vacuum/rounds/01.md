# Round 1: One row chain and one pinned horizon

Date: 2026-08-11

## Question

Can a small deterministic model distinguish snapshot visibility, heap-only
tuple (HOT) index-entry avoidance, and horizon-gated reclamation without
presenting itself as a PostgreSQL implementation or performance benchmark?

## Scenario

The model builds three committed row versions. Each `xmin` is the inserting
transaction identifier (XID), and each `xmax` is the XID that ended that
version's visibility interval:

```text
version 0: xmin=10, xmax=20, successor=1, value=100
version 1: xmin=20, xmax=30, successor=2, value=120
version 2: xmin=30, xmax=none, successor=none, value=140
```

Snapshots select values 100, 120, and 140. A same-page HOT-like chain keeps one
per-row index entry pointing to the chain's root item identifier. The control
changes an indexed key and accounts for one ordinary index entry per version.
An oldest retained `xmin` of 20 permits no reclamation; 40 permits reclamation
of the first two versions.

## Acceptance contract

Every fresh process must establish:

1. The three snapshots select the expected committed versions.
2. An XID listed as in progress remains invisible inside the snapshot bounds.
3. The HOT-like chain has one per-row ordinary index entry before and after cleanup.
4. The non-HOT control has three index entries before cleanup and one after it.
5. A pinned horizon at 20 reclaims zero versions.
6. A released horizon at 40 reclaims two versions.
7. The program prints its model exclusions before `CHECK=PASS`.

## Execution unit and replication

One `mvcc-hot-vacuum-probe --self-check` process is the execution unit. Each
host run executes eight generic and eight native fresh processes. A generic
build uses the compiler's baseline target features; a native build permits the
features reported by that host. The runner retains every exit status, output
stream, and Secure Hash Algorithm 256-bit (SHA-256) digest without replacing a
failed slot. An independent validator runs the binary again, recomputes the
expected receipt, and verifies all retained slots.

Replication checks deterministic behavior across process startup, compiler
target settings, and the two named hosts. It is not statistical sampling and
creates no performance interval.

## Why no timing comparison is justified

The model has no PostgreSQL buffer manager, indexes, concurrency, write-ahead
log, storage, lock manager, autovacuum scheduler, or cleanup contention. A
timing result would rank compiler output and process startup for a simulator,
not HOT or VACUUM behavior.

## Controls

- The in-progress-list case distinguishes snapshot bounds from commit status.
- The indexed-key-changing chain shares version lifetimes and page placement
  with the HOT-like chain.
- Pinned and released horizons use the same version array.
- Generic and native builds must produce byte-identical correctness receipts.
- Eight fresh processes retain process-level replication.
- Exported visibility and reclamation hooks retain linked code for disassembly,
  the machine-instruction listing from the final executable.
- The host runner builds from a clean, committed Git archive and verifies that
  source bytes remain unchanged.

## Evidence boundary

- **Observed:** process outputs, exits, hashes, host identity, toolchains,
  target features, binary symbols, and generated instructions.
- **Derived and validated:** source identity, archive identity, receipt counts,
  expected output, and the model's version and index-entry accounting.
- **Source-backed:** PostgreSQL 18 snapshot, HOT, isolation, visibility-map, and
  vacuum mechanics cited in `references.md`.
- **Not tested:** a PostgreSQL server, concurrent transactions, storage,
  write-ahead log (WAL), autovacuum scheduling, throughput, latency, or a
  production database.

## Promotion gate

Commit and push the source candidate before retained measurement. Run that
exact commit on the required literal Arm host and runtime-resolved `xxl` Secure
Shell (SSH) alias. Promote evidence only when both archives share one source
archive hash, all 32 fresh processes pass, the independent validators pass,
linked-code inspection succeeds, and every workspace gate succeeds on both
hosts. A workspace gate is one required format, test, lint, benchmark-build, or
documentation command from the repository root.
