# Round 1: Keep device reachability separate from ownership

Date: 2026-08-18

## Question

Can a small executable model catch a wrong address, a reversed transfer
direction, a stale mapping, simultaneous central processing unit (CPU) and
device access, a mismatched completion, or incorrect segment counts that an
input-output memory management unit (IOMMU) alone cannot?

A mapping generation, also called an epoch, numbers one lifetime of a mapping
so old work can be rejected. Scatter/gather means one transfer described by a
list of separate memory segments. A page pin prevents backing pages from moving
or disappearing. Cache maintenance cleans or invalidates cached bytes for a
device that does not automatically share cache-visible bytes with the CPU,
called a noncoherent device. A device register is a hardware control location,
not ordinary process memory.

This round does not perform direct memory access (DMA), program an IOMMU, pin
pages, maintain caches, access a device register, or measure device or
translation performance.

## Acceptance contract

Each required Linux host must:

1. verify a Git-created source archive against its full commit identity and
   Secure Hash Algorithm 256-bit (SHA-256) digest, a content fingerprint;
2. record the Secure Shell (SSH) target label, resolved hostname, architecture,
   kernel, CPU model and available count, page size,
   compiler and Rust toolchains, meaning their exact versions; target features,
   meaning compiler-reported instruction capabilities; build flags, meaning
   the exact compiler options; visible IOMMU state; and relevant kernel
   configuration;
3. confirm that `xxl` resolves at run time to a 64-bit x86 (`x86-64`) host and
   that the literal Arm target reports 64-bit Arm (`AArch64`);
4. pass the Rust package's, or crate's, tests and deterministic probe;
5. run eight generic builds, using the compiler's portable target defaults, and
   eight native builds, which may use features of that host, in fresh probe
   processes with no retry and byte-identical expected output;
6. retain linked disassembly, a decoded machine-instruction listing, for the
   named translation and DMA-mask test functions; a DMA mask states the largest
   device address allowed by the device's address width;
7. prove that the extracted source manifest, a sorted file-and-digest inventory,
   is unchanged after execution; and
8. produce another manifest over every retained receipt, meaning a saved
   evidence record.

One independently launched probe process is one replication unit. There are no
inner timing samples. The two build modes check portability and generated code;
they are not performance treatments.

## Expected state changes

The probe begins with CPU ownership. It maps a contiguous 16-kibibyte (KiB)
input-output virtual address (IOVA) aperture, meaning an allowed address range,
over four noncontiguous 4 KiB physical pages. It submits descriptor 41, where a
descriptor is the small record that tells the device what work to do, and then
checks:

- a valid device write translates to the expected physical page and offset;
- a range beyond the half-open aperture, which includes its start but excludes
  its end, is rejected;
- an intentionally wrong offset inside the aperture still translates;
- a direction mismatch and stale mapping epoch are rejected;
- CPU access and early unmap fail while the device owns the payload;
- an unrelated completion token fails and comes back to the caller, so its
  own mapping still completes;
- a device-reported descriptor that the mapping does not have in flight
  fails;
- the matching completion returns CPU ownership; and
- unmap rejects the merged hardware count and accepts the original
  scatter/gather count.

The in-aperture success is deliberate. It demonstrates that address isolation
cannot validate the payload protocol, meaning the higher-level rules for what
the transferred bytes should contain.

The evidence names several Linux mechanisms. A software input-output
translation lookaside buffer (SWIOTLB) copies through a device-reachable bounce
buffer. Virtual Function input/output (VFIO) is Linux's framework for device
access from a process outside the kernel, called userspace. The IOMMU file
descriptor (IOMMUFD) application programming interface (API) gives such a
process a kernel handle for IOMMU address spaces, mappings, and device
attachments. Shared virtual addressing (SVA) lets a capable device use process
virtual addresses. Address Translation Services (ATS) let a device cache
translations, and the Page Request Interface (PRI) lets it request a missing
translation.

## Evidence boundary

- **Measured:** process exit status, exact standard output (`stdout`), source
  and executable identity, host metadata, visible Linux system filesystem
  (`sysfs`) and kernel-configuration state, and linked generated code.
- **Source-backed:** Linux DMA API, IOMMU,
  SWIOTLB, VFIO, IOMMUFD, page-pinning, shared-virtual-addressing, and device
  input/output contracts in `references.md`.
- **Inferred:** how real devices would respond to address, cached-translation,
  cache-maintenance, reset, or missing-translation behavior.
- **Not tested:** device DMA, IOMMU map or the time to discard stale
  translations, called invalidation latency; input/output
  translation lookaside buffer misses, where a recent device translation is
  absent; ATS caches; PRI requests; SWIOTLB copies; VFIO isolation;
  memory-mapped input/output (MMIO) ordering; device-local memory; or direct
  device-to-device, or peer-to-peer, bandwidth.

No elapsed-time comparison is justified. Both treatments execute the same tiny
CPU model, and no comparable authorized device path is available. Timing it
would not answer the topic's performance question.
