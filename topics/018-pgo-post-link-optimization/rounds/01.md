# Round 1: profile choice is a deployment decision

The selected training distribution determines which execution frequencies the
optimizer treats as valuable.

## Decision rule

Choose a profile with an explicit target distribution, then retain an
unprofiled binary as the deployment control. Promote the candidate only when
the deployed workload mixture improves enough to repay profile collection,
build, validation, rollout, and rollback cost.

Let `p_i` be the deployed probability of workload class `i`, and let `T_i(b)`
be its cost under binary `b`. The expected cost is

```text
E_p[T(b)] = sum_i p_i T_i(b)
```

For an unprofiled binary `b0` and a candidate trained on distribution `q`,

```text
Delta(p, q) = E_p[T(b0)] - E_p[T(b(q))]
net benefit = H * Delta(p, q) - F
break-even horizon H* = F / Delta(p, q)
```

`F` includes profile collection, extra builds, artifact storage, validation,
rollout, and expected rollback work. Reject the candidate when `Delta(p, q)` is
non-positive. When `p` is uncertain, compare candidates by regret across the
credible workload mixtures instead of optimizing only the mean forecast.

## Technique boundary

| Technique | Observation identity | Transformation stage | Primary risk |
|---|---|---|---|
| Instrumentation compiler PGO | compiler-inserted counters in a training binary | recompile and relink | training perturbation and unrepresentative counts |
| Sample compiler PGO | sampled addresses and call chains mapped back to compiler IR | recompile and relink | skid, attribution, and incomplete call context |
| BOLT | addresses in the linked ELF image | rewrite the final image | stale image/profile identity and missing ELF metadata |
| Propeller | profile mapped to compiler-emitted basic-block sections | relink those sections | toolchain coupling and profile-to-section mapping |

Compiler PGO can alter inlining and function bodies before final layout exists.
Post-link layout sees exact addresses but cannot recover every source-level
transformation opportunity. Run compiler PGO first, then collect a fresh
post-link profile from that exact candidate.

## Failure modes

- A traffic-average profile can erase a rare path whose latency or correctness
  budget matters more than its count.
- Merging raw profiles by counter magnitude weights longer or busier runs more
  heavily. Required traffic weights need an explicit merge policy.
- Missing, stale, or mismatched profiles can silently reduce coverage unless
  the build treats profile diagnostics as a gate.
- Raw instrumentation profiles have a tool-version boundary. Use the
  `llvm-profdata` bundled with the compiler that generated them.
- Instrumentation changes code layout and can perturb the workload it measures.
  Shared counters can also add contention.
- Sample profiles inherit PMU skid, lost samples, call-chain limits, and symbol
  attribution errors.
- Reusing a BOLT profile after compiler PGO, relinking, or stripping can attach
  observations to the wrong image or remove required rewrite metadata.
- Hot-path gains can increase code size, instruction-cache pressure, startup
  faults, or cold-path latency.
- A statistically narrow interval does not establish a mechanism. Inspect the
  exact final code and retain an identity control.

## Focused inference

The `alpha`-trained and `beta`-trained binaries differ only through the profile
consumed by `rustc`. Their comparison isolates profile choice within one
toolchain invocation pattern; it does not isolate one machine instruction or
one optimizer pass. The baseline-copy comparison estimates noise in the same
measurement path. The retained code-generation files establish what the
compiler emitted, while timing records establish elapsed time for the named
processes. Any causal account connecting those facts remains an inference that
needs additional controls.

## Observed result

Both current Linux dev machines emitted the expected guarded direct calls, but
the alpha-trained candidate lost to the unprofiled baseline on both measured
workloads. The slowdown was about 1% on the probed AArch64 host and 11% to 15%
on the probed x86-64 host. Profile choice was unresolved on the AArch64 host;
on the x86-64 host, each trained candidate was faster than the other PGO
candidate on its own training workload.

These results reject the shortcut that successful devirtualization implies a
speedup. They do not identify the responsible mechanism. See the
[host-specific records](../measurements/README.md) for intervals, code
generation, provenance, and scope.
