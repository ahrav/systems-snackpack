# Round 1: Keep the parcel owned across cancellation

Date: 2026-08-20

## Question

Can one deterministic probe expose both the memory cost of values retained
across `.await` and the application-state loss caused by committing before
`Pending`?

## Acceptance contract

Each required Linux host must:

1. compile one exact `state_and_cancellation.rs` source with the recorded rustc
   version, native target features, and build flags;
2. record the Secure Shell (SSH) target label, resolved hostname, architecture,
   kernel, central processing unit (CPU) model and available count, toolchain,
   target features, and source digest;
3. confirm the literal Arm host is `aarch64` and runtime-resolved `xxl` is
   `x86_64`;
4. run eight fresh processes without retry and require byte-identical output;
5. require equal checksums, two polls for each generated future, parcel loss in
   the unsafe loser, parcel preservation in the safe loser, six wake calls, and
   final `PASS`;
6. retain Rust Mid-level Intermediate Representation (MIR), assembly, object
   code, symbols, and linked disassembly; and
7. retain a digest manifest for every result file.

One launched process is one replication unit. Polls within a process are state
transitions, not independent samples.

## Expected state changes

The generated futures perform the same 4 kibibyte (KiB) buffer work. The first
uses the buffer after suspension. The second reduces it to a checksum before
suspension. The exact sizes can vary by compiler, but the first must contain at
least 4,096 bytes and the second must remain below that value.

The two-queue race starts with parcel 11 in the left queue and parcel 22 in the
right queue. Both receive futures return `Pending`; the left future then wins.

```text
unsafe right: queued(22) -> staged(22) -> Pending -> drop -> empty
safe right:   queued(22) -> Pending -> drop -> queued(22)
```

## Evidence boundary

- **Measured:** exact source and output digests, host metadata, future sizes,
  process-level state transitions, MIR storage, native symbol sizes, and
  instruction ordering.
- **Source-backed:** Rust polling, pinning, waking, and Tokio task, selection,
  cancellation, join, and shutdown contracts in `references.md`.
- **Inferred:** the source-level ownership mechanism explaining the generated
  ordering and the Arm model name inferred from its measured processor ID.
- **Not tested:** a production executor or channel, multithreaded races,
  scheduler fairness, wake coalescing, input/output readiness, runtime memory
  allocation, cancellation latency, throughput, or cross-architecture
  performance.

The receipt checks assume the authorized Linux host and invoker are trusted.
They bind source and evidence; they are not an adversarial execution sandbox.

No elapsed-time comparison is justified. The probe contains a manual
single-threaded driver, not the runtime paths whose performance the topic
discusses.
