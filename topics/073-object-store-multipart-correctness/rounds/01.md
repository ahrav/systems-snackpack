# Round 01: receipt normalization and unknown completion

Date: 2026-10-10. This round uses an immutable attempt key, consecutive planned
part numbers, and immutable bytes for every retry of a part. The runnable model
rejects missing/out-of-range/conflicting receipts and preserves uncertain
completion outcomes. It does not send S3 requests.

Three correct finalization alternatives are compared: copy/sort, BTreeMap, and
dense slots. Independent oracle tests cover 19,531 short streams, maximum length,
and 28 completion/identity combinations. Four unit tests and one doctest pass.

The final committed-source local campaign ran 108 fresh processes on Apple M1
Pro. Dense slots won five cells under the declared all-pairs 5% rule. The 10,000
ordered-part case remains unresolved. [Results](../results.md) include medians,
min/max, timing boundaries and source identity. [The receipt](../EVIDENCE_RECEIPT.json)
links retained raw data, builds, host metadata, and seven passing workspace gates.

Both required Linux hosts rejected Midway authentication before host verification
or source transfer. Their exact-source replay remains pending. No Linux, S3
throughput, cold-start, or architecture-wide selection is claimed.

Earlier runs are retained separately. Independent review found runner provenance
gaps, which were repaired before the final run. The benchmark binary remained
byte-identical; no further timing was run to obtain a preferred selection.
