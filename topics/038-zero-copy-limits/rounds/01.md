# Round 1: Which copy disappears?

Date: 2026-08-17

## Question

For one prewarmed file sent through an IPv4 loopback TCP socket, how do
buffered `pread` plus `send`, `sendfile`, and `splice` differ in elapsed time,
sender and receiver CPU time, and call count? Which separate lifetime contract
does `MSG_ZEROCOPY` impose on generated application buffers?

This round does not test physical storage, a network device, DMA, a remote
receiver, TLS, congestion, or production concurrency.

## Acceptance contract

Before timing can be promoted, each required host must establish:

1. The generic and native C builds pass compilation with warnings as errors.
2. The Rust contract probe and crate tests pass.
3. Buffered, `sendfile`, and `splice` send exactly 16,777,219 expected bytes;
   the receiver checks every byte.
4. Timing methods send the same immutable 512 MiB file with the same 256 KiB
   requested chunk and report clean receiver status.
5. The source file is prepared once and read once before timing. This makes
   residency likely but does not prove every page remained resident.
6. Every timing process succeeds on its first and only attempt. A failed or
   malformed process invalidates the run.
7. The fixed seed `38017` reconstructs the complete schedule, including all
   method labels, positions, blocks, and raw-output hashes.
8. Both generic and native `MSG_ZEROCOPY` controls verify all 524,288 received
   bytes, retain the buffer through completion, and cover identifiers 0 through
   7 with validated inclusive completion ranges.
9. Linked generated-code inspection finds the expected external calls and
   records its limits.

## Treatment and analysis units

One fresh `transfer-probe` process is one treatment application. Each paired
block uses either `ABBA` or `BAAB` order, so both labels appear twice and occupy
early and late positions. There are eight blocks for each pair:

- buffered versus `sendfile`;
- buffered versus `splice`; and
- buffered label A versus buffered label B.

The final pair is the A/A plumbing control: both labels run the same method.
The schedule therefore contains 96 fresh timing processes. Four rows in one
complete block produce one log-ratio contrast. Repeated receive calls inside a
process are implementation work, not independent samples.

For positive time `t`, each block contributes the mean log time for label B
minus the mean log time for label A. The reported point estimate is the
exponential of the mean of eight block contrasts. Values below one mean B took
less elapsed time than A. The sample standard deviation of block log contrasts
is the primary dispersion report. A transformed Student-t 95-percent interval
is descriptive for this run. Sequential blocks on one shared host do not prove
independence or normality, so the interval is not a prediction bound.

## Timer boundary and controls

`transfer_sec` begins after socket and input-file setup. It intentionally
includes application-buffer allocation and release for the buffered path. It
also includes pipe creation and close for the `splice` path. Those setup choices
are method-specific and asymmetric. The run also records `setup_sec`,
`total_sec`, sender CPU, receiver CPU, and shell-observed outer time. An elapsed
difference cannot be assigned solely to byte-copy removal.

Other controls are:

- equal logical bytes, requested chunk, prepared file, and loopback transport;
- a one-pass file warmup before the fixed schedule;
- exact-byte correctness runs outside the timing schedule;
- fixed sender and receiver CPU affinity inside each process;
- alternating order within complete blocks;
- a buffered A/A path for label, schedule, parser, and analysis plumbing;
- no result-driven stopping and no retry;
- per-process call, socket-buffer, CPU, byte, and status observations;
- generic and `-march=native` correctness builds; and
- exact source, executable, raw-output, and retrieved-archive hashes.

The A/A result is not a universal noise floor or an equivalence test. Order
balance addresses only the chosen block structure; it does not remove nonlinear
drift, carryover, or shared-host interference.

## Evidence classification

- **Measured:** exact received bytes, elapsed and CPU intervals, call counts,
  pipe and socket-buffer sizes, completion records, process order, host and
  toolchain metadata, hashes, and linked call sites.
- **Derived:** complete-block log contrasts, geometric ratios, sample
  dispersion, descriptive Student-t intervals, page spans, and capacity-model
  outputs.
- **Source-backed:** Linux interface contracts in `references.md`.
- **Inferred:** copy, cache, page-reference, scheduler, and protocol mechanisms
  unless another observation isolates them.
- **Not tested:** physical storage, a NIC, DMA, remote delivery, TLS, congestion,
  concurrent load, slow-request tails, energy, or generality across processor
  families.
