# Round 1: Narrow locator versus covering payload

Date: 2026-08-10

## Question

For one deterministic, memory-resident point-lookup workload, how does a
narrow sorted index plus an unpredictable payload fetch compare with a wider
sorted entry that contains the payload?

The result applies only to this layout kernel. It does not estimate a database
query, page miss, transaction, concurrent split, log write, or storage device.

## Precise model

Both representations contain the same sorted keys and return the same two
64-bit payload values.

- The narrow entry contains a 64-bit key and a row locator. The locator indexes
  a separately allocated payload array whose order is a deterministic
  permutation of key order.
- The covering entry contains the 64-bit key and both payload values.
- The query stream deterministically mixes hits and misses.
- Each treatment uses the same binary-search semantics and accumulates one
  checksum. A reference oracle validates every result before timing.

Logical byte counts describe modeled fields. Rust type sizes and alignments are
also reported because compiler layout can differ from the logical model.

## Cost model

For tree level `l`, let `r_l` be the probability that its page is resident,
`C_hit` the resident-page cost, `C_miss` the nonresident fetch cost, and
`C_queue` any wait behind other work. Then:

```text
C_page(l) = r_l * C_hit + (1 - r_l) * (C_miss + C_queue)
```

For height `h`, in-page search cost `C_search`, synchronization cost `C_sync`,
base-fetch cost `C_base`, and probability `q_cover` that the index covers the
query:

```text
C_lookup = sum(l = 1..h, C_page(l) + C_search(l) + C_sync(l))
           + (1 - q_cover) * C_base
```

The experiment holds pages, synchronization, and storage outside its model. It
measures only the in-memory search and payload-access terms for two concrete
layouts.

## Execution unit and replication

One fresh probe process is the execution unit. It constructs deterministic
data, validates both layouts, performs one untimed warmup, and then times one
treatment. The runner executes twelve complete four-process blocks: six
`narrow, covering, covering, narrow` blocks and six with the reverse order.
That yields 48 fresh processes and 24 observations per treatment on each host.

The primary contrast is the within-block geometric mean of the narrow-to-
covering elapsed-time ratio. The report includes its point estimate, range,
order strata, and a sign interval over the twelve complete block contrasts.
The interval has exact 96.14% coverage only under the sign method's independent,
exchangeable, continuous-contrast assumptions. Shared host conditions can
violate independence, so the report labels that coverage nominal. The interval
describes variation between retained blocks in this run window; it is not an
interval over machines, processors, compilers, or workloads.

## Controls

- Fixed seeds make data, locator permutation, and queries repeatable.
- A reference oracle checks hits, misses, and returned payload values.
- Both treatments must produce the same checksum in every process.
- Construction, correctness checks, and warmup are reported separately from
  steady-state elapsed time.
- Alternating orders reduce monotonic warmup, thermal, and background-load
  bias within each block.
- Generic and native builds must pass identical correctness checks.
- Exported lookup hooks are inspected in the linked executable on each host.
- The exact pushed source archive is hashed before remote execution.

Fresh processes share a host, kernel page cache, thermal environment, and
background daemons. Replication does not make them independent draws from a
larger machine population. No A/A calibration, which compares a treatment with
itself to estimate harness noise, is included.

## Expected observations

The covering path should avoid one data-dependent payload-array access. Its
wider sorted entries should touch more index bytes. Either effect may dominate;
the benchmark is designed to expose that tradeoff rather than guarantee a
winner.

Generated code should retain the locator-based payload load in the narrow hook
and read payload fields from the matched covering entry in the covering hook.
Instruction choice may differ by compiler and target. Source shape alone is
not evidence of final machine code.

## Evidence boundary

- **Measured:** per-process steady elapsed time, setup time, warmup and checking
  overhead, checksums, and paired block contrasts.
- **Observed:** host identity, target features, toolchains, logical and Rust
  layout sizes, binary hashes, symbols, and linked-executable disassembly.
- **Derived:** medians, geometric means, order strata, dispersion, and the sign
  interval computed from retained process records.
- **Inferred:** cache-locality mechanisms consistent with the representation
  and observed loads. Hardware counter events are not measured.
- **Unknown:** cold-page behavior, buffer-manager policy, transaction
  visibility, latches, concurrent writers, splits, logging, compression,
  filesystem and device input/output, planner choices, and production latency.

## Promotion gate

Commit and push the source candidate before retained measurement. Run that
exact commit on the required Arm host and the runtime-resolved `xxl` host.
Promote results only when both archives name one source commit, share one source
archive hash, pass the correctness oracle, retain every process result, expose
both inspection hooks, and pass the workspace validation gates.
