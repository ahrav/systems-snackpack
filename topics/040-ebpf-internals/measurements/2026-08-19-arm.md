## Question and boundary

This run asks whether one exact committed probe reaches the expected Linux
permission, verifier, translation, socket-attachment, and packet-action
boundaries on the required Arm host. It does not measure elapsed time. The
250-millisecond drop timeout is a correctness threshold.

## Observations

- The ordinary process exited 77. Both load attempts returned `EPERM`, and the
  verifier logs were empty. This is the observed host policy ordering.
- All eight independently launched privileged processes passed without retry.
- Every process rejected the invalid program with `EINVAL` and
  `jump out of range from insn 0 to 101`.
- Every process loaded both valid programs, received the exact 14-byte accept
  payload, and observed a successful send followed by a receive timeout for
  drop.
- Both translated programs were 16 bytes and matched the submitted encodings.
- All eight accept JIT blobs were the same 64 bytes. All eight drop JIT blobs
  were the same 64 bytes. Each of the 16 disassemblies contained `ret` at
  offset `0x30`, followed by `nop`, a load, and an indirect branch ending in
  `br x10`.
- The Rust library/example tests and deterministic example passed from the same
  Git archive.

The visible native bodies shared one 64-byte template. The semantic difference
was `mov x7, #-1` for accept and `mov x7, #0` for drop. The template also
contained `paciasp`, `autiasp`, `ret`, and a trailing load-and-branch sequence.
The receipt establishes those bytes; it does not establish why every template
instruction is present.

`bpf_prog_info` reported `run_cnt=0` and `run_time_ns=0`, while socket behavior
proved execution. The zero counters are expected with BPF runtime statistics
disabled and are not evidence that the programs did not run.
