# Round 1: Separate permission, verification, attachment, and action

Date: 2026-08-19

## Question

Can one small Linux experiment make four boundaries visible: permission to ask
for a program load, verifier rejection of an invalid program, just-in-time
(JIT) translation of accepted programs, and the observable action of attached
socket filters?

The experiment submits three two-instruction Extended Berkeley Packet Filter
(eBPF) programs with the raw `bpf()` system call. The invalid program jumps 100
instructions past its end. One valid program returns all one bits, which lets a
socket receive the complete packet. The other returns zero, which discards the
packet for that socket. The executable retrieves both the translated eBPF bytes
and the generated native bytes through `BPF_OBJ_GET_INFO_BY_FD`, a command that
returns kernel information about an object identified by a file descriptor.

## Acceptance contract

Each required Linux host must:

1. verify a Git-created source archive against its embedded commit identity and
   Secure Hash Algorithm 256-bit (SHA-256) digest, a content fingerprint;
2. confirm its fully qualified hostname and architecture against the supplied
   Secure Shell (SSH) target label, including resolving `xxl` to a 64-bit x86
   (`x86_64`) host at run time;
3. record the kernel, central processing unit (CPU) identity and online count,
   build flags, relevant sysctls, effective capabilities, BPF filesystem and
   kernel BPF Type Format (BTF) state, and selected kernel configuration;
4. compile the C probe with
   `gcc -O2 -g -std=c11 -Wall -Wextra -Werror`;
5. run one ordinary process and require the documented permission outcome when
   unprivileged BPF is disabled;
6. launch eight fresh privileged probe processes without retry. Every process
   must reject the out-of-range jump, load both valid programs, return the
   submitted translated instructions, expose nonempty JIT bytes, receive the
   exact accept payload, and time out on receive for the drop filter;
7. retain each process stream, submitted and returned byte identities, verifier
   log, program-information lengths, and generated blobs;
8. disassemble the JIT bytes with the host's native GNU `objdump` target;
9. pass the Rust package tests, examples, documentation, and lints; and
10. prove that the extracted source manifest is unchanged after execution and
    retain a digest manifest over the evidence bundle.

One independently launched privileged process is one replication unit. The
loopback send and receive happen inside that process. There are no inner timing
samples, and a 250-millisecond receive timeout is only a correctness threshold.

## Expected observations

The ordinary process reaches permission policy before useful verifier
diagnostics on the retained hosts: both loads return `EPERM`, the verifier logs
are empty, and the process exits 77. The observed
`kernel.unprivileged_bpf_disabled=1` setting cannot be changed back to zero;
value `2` is the administrator-reversible disabled state. This order is a
host-policy observation, not a universal Linux promise.

The privileged process must report:

- `EINVAL` and `jump out of range from insn 0 to 101` for the invalid program;
- two processed instructions for each accepted program;
- the exact 16-byte translated encoding for each submitted valid program;
- nonempty JIT bytes and an architecture-appropriate native disassembly;
- a received 14-byte `topic40-accept` payload for the accept program;
- a successful send followed by a receive timeout for the drop program; and
- `outcome=all_correctness_checks_passed`.

Program identifiers and process identifiers can change between fresh
processes. JIT lengths and bytes may vary with architecture, kernel build,
hardening, and other host policy. The validator requires internal identity and
valid native code, not equality between hosts.

## Evidence boundary

- **Measured:** process status and streams; submitted and kernel-returned eBPF
  encodings; verifier log; JIT lengths, bytes, and native disassembly; socket
  receive behavior; exact source and executable identity; and visible host
  configuration.
- **Source-backed:** verifier state tracking, object lifetime, program-type,
  map, ring-buffer, JIT, and sysctl contracts listed in `references.md`.
- **Inferred:** the cost decomposition in `README.md` and how another workload
  would divide time among hook, instructions, helpers, maps, output, and
  contention.
- **Not tested:** Express Data Path (XDP), traffic control, control-group programs, tracing, Linux
  Security Module programs, maps, helpers, ring-buffer loss, hardware offload,
  driver behavior, production traffic, or elapsed-time performance.

`BPF_PROG_RUN` can execute a loaded program with supplied context without its
normal attachment. This round instead attaches real socket filters, but its
loopback path is still not evidence about other hooks or drivers.

No timing comparison is justified. The probe tests admission, generated code,
attachment, and action with two constant-return socket filters. Timing would be
dominated by process, system-call, socket, and timeout mechanics and would not
answer a production eBPF performance question.

## Retained result

Host-specific notes and raw archives are added only after the exact-source run
passes on both required hosts. Until then, this round defines the measurement
contract but claims no checked-in host result.
