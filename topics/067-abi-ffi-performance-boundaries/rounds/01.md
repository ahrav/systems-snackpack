# Round1: crossing shape versus whole-request cost

The running request transforms4096 u64 values and reduces them modulo2^64.
Per-value C makes4096 crossings; chunks256 makes16; a full batch makes1. The
copied candidate also allocates/copies/releases each request. The Rust candidate
keeps implementation visible in the caller's language. Separate native C objects
with no LTO keep the chosen foreign boundary real.

Model: scalar N(C+Ws); batch ceil(N/B)C+N*Wb; copy adds N*M+A. N is item count,
B batch size,C simplified crossing cost,Ws/Wb per-item work,M copy cost per item,
and A allocation/release. For4096 items,B4096,C4ns,Ws=Wb1ns,M0.5ns,A100ns,
illustrative totals are20480ns,4100ns,6248ns. These are derived assumptions,
not measurements. A batch changes more than C: vectorization, locality, loop
control and copying can change. Fixed total bytes does not isolate call cost.

Four unit tests cover independent-u128 equivalence across sizes/work, empty/null0,
overflow values, immutability and chunk partitioning; a doctest checks the safe API.
An arbitrary C pointer cannot become a safe Rust slice just because null/length
checks pass. The caller must establish allocation, initialization and lifetime.

Prefer the simplest correct measured winner for a declared workload. If C is
required, compare batch shapes rather than assuming language replacement is viable.
Borrow only until synchronous completion; retained asynchronous use needs its own
ownership/quiescence protocol. Crossing reduction remains observed even if added
work offsets its end-to-end gain. See exact-source results and limitations.
