# Round 1: measure dependent-load latency under streaming traffic

## Question

On each required Linux host, how does large-working-set dependent-load time
change after eight other pinned physical cores prove that they are consuming
private read-only buffers? How many useful source bytes do those workers
consume over the complete run epoch?

The experiment measures exact-host elapsed time, application useful bytes,
correctness, placement canaries, and linked code. It does not measure DRAM-only
service time, memory-controller saturation, queue depth, row hits, bank
conflicts, refresh, channel mapping, or a deployed scheduling policy.

## Frozen comparison

- Source: one path-limited Git archive from the Topic 49 source commit.
- Build: GNU Compiler Collection (GCC) 11.5, `-O3 -g -std=gnu11 -Wall -Wextra
  -Werror -march=native -pthread`.
- Probe: one deterministic 512 MiB cycle of 64-byte nodes and four timed full
  traversals after prefault and treatment-state warmup.
- Control: one 8 KiB dependent cycle measured in the same treatment period.
- Workers: eight distinct physical cores on the probe's NUMA node, each with a
  private 128 MiB read-only stream buffer.
- Placement: the probe and workers pin before first-touch initialization.
- Memory policy: every thread applies `MPOL_BIND` to the topology-selected NUMA
  node before allocating. A failed bind fails the process.
- Page state: anonymous mappings request `MADV_NOHUGEPAGE`; the receipt records
  the call result and mapping evidence. This request does not prove final page
  size by itself.
- A treatment: create and initialize the workers, then leave them idle.
- B treatment: create and initialize the same workers, release them, and wait
  until every worker has completed one stream chunk before either timed walk.
- Warmup: 750 ms under the selected treatment before the timed work.
- Primary replication: 12 complete four-process blocks, six `ABBA` and six
  `BAAB`, seed-shuffled before collection.
- A/A control: four loaded/loaded blocks, two of each template, through the two
  label and output paths.
- Reset: every letter is a fresh process followed by a one-second quiet interval.
- Stopping: block counts, seed, input, CPUs, and commands are fixed before
  collection. Failed attempts remain in the receipt.

## Analysis

For period `p`, let `x_p` be the natural logarithm of large-chain nanoseconds
per load. An `ABBA` block uses:

```text
d = ((x2 + x3) - (x1 + x4)) / 2
```

A `BAAB` block uses:

```text
d = ((x1 + x4) - (x2 + x3)) / 2
```

Exponentiating the mean of 12 block contrasts gives the geometric loaded/idle
ratio. Report every block, the sample standard deviation of log contrasts, the
two-sided 95% Student-t interval, template-specific estimates, medians, and
ranges.

The interval covers complete process-block variation on one exact host, binary,
input, and run window. It assumes independent, approximately normal block
contrasts. It does not cover other machines, builds, time windows, or processor
families.

The A/A run checks artifact, argument, label, parser, schedule, and output-path
symmetry. Four blocks do not calibrate a false-positive rate or define a noise
floor.

## Acceptance contract

1. The controller supplies the archive digest, expected hostname, and expected
   architecture before remote extraction.
2. The literal Arm target reports `aarch64`. Runtime-resolved `xxl` reports
   `x86_64`, and its alias and backing hostname are recorded.
3. The receipt records CPU model, kernel, topology, cache, NUMA nodes, online and
   selected CPUs, sibling sets, page policy, available CPU count, compiler,
   build flags, native target, PMUs, and load average.
4. Source, runner, analyzer, validator, archive, and native binary Secure Hash
   Algorithm 256-bit (SHA-256) digests remain fixed.
5. Every process validates affinity, deterministic checksums, fixed input,
   treatment echo, page advice, zero timed minor and major faults, and result
   fields.
6. All attempts remain in chronological order. No failed period is silently
   replaced.
7. Every block has the declared template and two periods for each label.
8. The exact linked walker, stream kernel, and timed caller remain inspectable.
9. The analyzer and independent receipt validator recompute the same summaries.
10. Timing, useful source bytes, code generation, placement intent, observed
    metadata, and mechanism inference remain separate claims.

## Useful-byte boundary

Workers reset and wait at a run epoch. The main thread records the start,
releases them, waits until every loaded worker acknowledges one complete chunk,
times the small control and large dependent walk, requests stop, and joins every
worker before recording the run-epoch end. Workers publish only complete 256
KiB chunks observed before the stop request. The join keeps any final source
reads during worker drain inside the measured epoch.

With eight workers, the uncounted tail is at most:

```text
8 * 256 KiB = 2 MiB
```

If `L` is the published lower byte count and `A` is the actual source byte
count during the run epoch, the receipt guarantees:

```text
L <= A <= L + 2 MiB
```

The upper bound is inclusive because a worker can finish one chunk before stop
but observe stop before publishing it. Every loaded worker must publish at
least one complete chunk. Idle lower and upper byte and rate bounds are exactly
zero.

The receipt reports lower and inclusive-upper useful-byte rates over the full
run epoch: release, all-worker acknowledgement, small control, and large probe.
It also includes stop publication and worker drain through termination. These
rates are not large-probe-only rates and do not equal cache, interconnect, or
memory-controller traffic.

The receipt reports minor faults, major faults, and voluntary and involuntary
context switches twice around the large dependent walk: process-wide
`getrusage(RUSAGE_SELF)` deltas and probe-thread-only
`getrusage(RUSAGE_THREAD)` deltas. A process-wide minor or major fault fails the
period.

## Evidence boundary

The large-chain contrast establishes an exact-host loaded-treatment effect. A
stable small-chain control weakens effects that operate uniformly across both
timed windows, but it does not exclude work specific to the later large-chain
window. Neither result identifies a DRAM mechanism without matching
model-specific cache, offcore, and controller evidence.
