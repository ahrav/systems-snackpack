# Round 1: Unknown reply after a committed effect

Date: 2026-08-09

## Question

When two callers race with one request key and the winner loses its reply, can
the retry recover one effect without treating equal parameters as identity?

## Deterministic schedule

The probe uses a condition variable to force this order:

1. The first thread claims `order-42` as `IN_PROGRESS`.
2. The duplicate thread checks the same key before the first thread completes.
3. The duplicate observes `IN_PROGRESS` and performs no effect.
4. The first thread commits one effect and one completed receipt.
5. The caller treats the reply as lost and retries the same key.
6. The retry replays resource 1 without increasing the effect count.

The probe then checks a changed fingerprint, a new key with identical input,
generation-fenced takeover, and both non-atomic split-write orders.

## Acceptance contract

Each fresh process must establish eight results:

1. One same-key contender owns the request.
2. The concurrent duplicate observes `IN_PROGRESS`.
3. A retry after a lost reply replays resource 1 with one effect.
4. The same key with changed input returns `PARAMETER_MISMATCH`.
5. A new key with the same input creates resource 2.
6. A takeover fences the stale owner and creates only resource 3.
7. Effect-before-receipt produces two effects after retry.
8. Receipt-before-effect produces a false replay with zero effects.

The safe store must retain a one-to-one mapping between completed receipts and
modeled effects.

## Execution unit and replication

One fresh `idempotency-probe --self-check` process is the execution unit. The
fixed schedule contains eight slots. The retained host run executes all eight
slots for generic and native builds. It records every exit, output, standard
error stream, and SHA-256 digest without replacing a failed slot.

Replication checks process startup, thread scheduling under the forced gate,
and deterministic receipt production. It is not statistical sampling and
creates no performance interval.

## Why no timing comparison is justified

The `Mutex` models a transaction boundary. Its elapsed time omits durable log
flushes, unique-index contention across processes, network delay, receipt
storage, external side effects, and recovery. A local timing result would rank
two simulator paths rather than idempotency designs.

## Controls

- The condition variable forces the duplicate to inspect `IN_PROGRESS`.
- A different key with the same fingerprint prevents parameter equality from
  passing as request identity.
- A changed fingerprint with the same key tests misuse detection.
- A stale generation must fail before it appends an effect.
- Both split-write orders expose duplicate-work and lost-work controls.
- Native and generic builds must produce identical correctness receipts.
- Stable exported hooks retain begin-decision and fencing code for disassembly.

## Evidence boundary

- **Observed:** process outputs, exits, hashes, host identity, toolchain, target
  features, binary symbols, and generated instructions.
- **Derived and validated:** receipt digests, source identity, exact process
  count, and the in-memory receipt-to-effect bijection.
- **Inferred only:** crash behavior of a durable database, network ambiguity,
  external-effect semantics, retention safety, and production authorization.

commit on the required literal Arm host and runtime-resolved `xxl` host.
`run_host.sh` builds from a verified Git archive, checks the pinned toolchain,
