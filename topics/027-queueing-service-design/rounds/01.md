# Round 1: Service-time variability in a bounded FCFS queue

Date: 2026-08-06

## Question

At matched offered mean service work and nominal utilization, how does the
prescribed increase in service-time variability change queue wait, rejection,
and goodput in this exact bounded single-worker system?

## Treatments

- `A`, fixed: every offered request receives `1x` calibrated service work.
- `B`, variable: within every ten offered requests, nine receive `0.25x` and
  one receives `7.75x`. Its deterministic group position comes from the
  recorded seed.
- A/A: both labels receive the fixed treatment while traversing the same label,
  order, runner, output, and analysis paths.

Both main treatments offer exactly `10x` work per ten requests. Relative to
the shared base work, fixed service has offered `Cs^2 = 0` and variable service
has offered `Cs^2 = 5.0625`.

## Units and fixed horizon

| Role | Unit |
| --- | --- |
| Treatment application | One fresh `queue-probe` process running one period |
| Assignment unit | One four-period block receives one predeclared template |
| Analysis unit | One complete four-period block contrast |
| Subsample | One of 8,000 request attempts inside a period |
| Sampling boundary | One exact binary, host, CPU list, and run window |
| Interference boundary | Host state can persist across fresh processes and blocks |

The experiment stops after the fixed schedule, not after a statistical result:

```text
main: BAAB ABBA BAAB ABBA ABBA BAAB ABBA BAAB
A/A:  ABBA BAAB BAAB ABBA
```

This is a predeclared restricted schedule, not post-result randomization.
Schedule seed `27_082_026` identifies it. Every letter is a fresh process, so
each host schedules 32 main and 16 A/A invocations. Every invocation offers
exactly 8,000 deterministic open-loop arrivals to one FCFS worker through four
waiting slots. The per-host `1x` calibration targets about 200 us; the arrival
interval is selected for nominal `rho = 0.9` from that offered mean.

## Records and estimands

For every request retain intended arrival, actual generator attempt, service
start when admitted, completion when completed, or rejection at admission.
Also retain source and binary identity, process assignment, calibration,
interval, CPU boundary, exit status, and checksum.

For invocation `p`, define `mean_wait_p` over completed requests only. In main
block `b`, with two periods per label, the primary contrast is:

```text
D_b = mean(mean_wait_p for the two B periods)
    - mean(mean_wait_p for the two A periods)
```

Periods receive equal weight; request rows are not pooled across periods. The
primary estimate is the arithmetic mean of the eight `D_b` values, with a
two-sided 95% Student-t interval over the eight complete block contrasts
(`df = 7`). The estimand is the conditional completed-request mean-wait
difference for this bounded system. It is not the wait of rejected requests.

The interval is model-based. It treats the eight sequential block contrasts as
independent enough and approximately normal for the Student-t calculation.
The ABBA/BAAB balance limits additive within-block order drift; it does not
establish block independence or remove carryover and nonlinear host drift. The
interval covers block-to-block variation inside this one run window, not
host-day, fleet, workload, or source variation. Independent run-window
replication would be required to estimate those sources of uncertainty.

Secondary outcomes are completed-request p50 and p99 queue wait, rejection
fraction over offered requests, generator lateness, and goodput. Report their
blockwise treatment contrasts or ratios and dispersion separately. They are
diagnostic and do not replace the primary fixed-horizon inference. Offered,
admitted, completed, and rejected counts stay separate.

The four A/A block contrasts use the same construction with identical fixed
service. They diagnose label, order, runner, and analysis asymmetry. They do
not prove independence, adequate power, production relevance, or absence of
all bias.

## Failure and no-replacement rule

Retain every attempted invocation. A missing row, invalid timestamp order,
wrong assignment, configuration drift, checksum failure, process failure, or
source/receipt mismatch invalidates that period and its block. Do not replace a
period after observing its outcome. The confirmatory run is incomplete if the
fixed eight main blocks are not valid as scheduled. A retry uses a new run
identity and repeats the entire schedule; a source correction requires a new
commit and exact-candidate rerun on both hosts.
